# Literature synthesis — 14B-constrained ViFinQA strategy

## Scope and compliance gate

ViFinQA is treated as a **maximum-14B** competition constraint, per the
organizer-rule clarification supplied to this project.  Do not assume that a
large teacher, closed API, or a newly published fine-tune is eligible merely
because it is useful during experimentation.  Before selecting a model, record
its base-model size, public release date, licence, and whether every inference
component is local and within the organizer rules.

## Paper 1 — T²-RAGBench

[T²-RAGBench](https://arxiv.org/pdf/2506.12071) studies the same unknown-context
text-and-table setting: retrieval precedes numerical reasoning.  Its key
transferable observation is that hybrid sparse+dense retrieval beats dense-only
base RAG, whereas their reranker and HyDE variants can degrade on text-table
documents.  This supports a ViFinQA design with metadata-gated lexical recall
plus a table/row semantic view—not an LLM-generated hypothetical document.

Their large generators are not eligible templates for a 14B setup.  Also, their
evaluation shows a large Oracle-context versus retrieved-context gap, so an
excellent program generator cannot compensate for missing evidence.

## Paper 2 — TabLaP

[TabLaP](https://arxiv.org/pdf/2410.12846) uses an LLM as a *planner* and a
Python interpreter for arithmetic.  This directly supports the project choice
to compile a typed plan to Pandas instead of asking a model to emit a numeric
answer.  Its answer-selection and trust modules are not portable as-is because
they use multiple LLM branches and a training history unavailable in ViFinQA.

Portable idea: execute every candidate program and reject candidates that lack
grounded operands, use the wrong requested unit, or fail schema constraints.

## Paper 3 — VLSP ViNumQA

[VLSP 2025 ViNumQA](https://aclanthology.org/2025.vlsp-1.25.pdf) is the closest
Vietnamese financial numerical-reasoning precedent.  Its constrained subtask
used a <=13B model cap and prohibited external/API use at training and
inference; this is analogous, not proof of ViFinQA policy.  Its best practical
patterns were Markdown table serialization, program/execution-oriented SFT,
and n-sampled program voting.  A 7–9B Qwen-family student was reported as a
viable efficient deployment in that benchmark.

Important transfer caveat: ViNumQA supplies the table context and gold programs;
ViFinQA requires report/table retrieval with dashboard-specific line IDs.
Therefore its program-generation recipe is **downstream** of evidence closure.
Its 235B-teacher distillation path must remain out of scope until explicitly
allowed by the ViFinQA organizer rules.

## Resulting design decision

Build one local <=14B program proposer only after a deterministic evidence
closure stage.  Serialize each selected evidence table to a compact Markdown
view, preserve raw CSV for execution, generate several typed programs, execute
them in a restricted Pandas environment, and vote only among candidates that
pass grounding/unit/type checks.  Keep top-k table evidence rather than
irreversibly filtering cells before the program step.
